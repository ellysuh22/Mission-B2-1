# B2-1 설계 전략 — 나만의 용돈 기입장 (budget_app)

> 이 문서는 "코드를 짜기 전에 어떻게 구성할지" 정한 설계 기록입니다.
> 평가 때 "왜 이렇게 만들었나요?"라는 질문에 이 문서의 결정 이유로 답할 수 있습니다.

---

## 1. 목표와 성공 기준

| 구분 | 내용 |
| --- | --- |
| 만들 것 | 파일(JSONL) 기반 콘솔 가계부. 미션 필수 기능 10개 + 보너스 4개 |
| 성공 기준 1 | 평가표 항목 1의 기능 체크가 모두 시연으로 확인된다 |
| 성공 기준 2 | 평가표 항목 2~4의 "어떻게/왜" 질문마다 **보여줄 파일 하나**가 정해져 있다 |
| 성공 기준 3 | 비전공자가 읽어도 따라갈 수 있게, 파일마다 역할이 한 문장으로 설명된다 |
| 제약 | Python 3.10 이상, 표준 라이브러리만, 옵션은 `--` 표기, 스택트레이스 출력 금지 |

## 2. 핵심 전략: "평가 질문 = 코드 위치"

| 평가 질문 | 보여줄 곳 |
| --- | --- |
| 모듈 책임을 어떻게 나눴나 (항목 2) | 폴더 구조 + 각 파일 맨 위의 "하는 일 / 안 하는 일" |
| 클래스 책임 경계 (항목 2) | `models.py`(데이터 모양) · `storage.py`(파일) · `services.py`(규칙) |
| update/delete 안전성 (항목 2) | `storage.py`의 `write_jsonl_atomic()` |
| 제너레이터 스트리밍 (항목 3) | `storage.py`의 `read_jsonl()` → `services.py`의 `search()` |
| 데코레이터 (항목 3) | `decorators.py` → `cli.py`의 `@log_execution`, `@handle_errors` |
| 타입 힌트 (항목 3) | 모든 함수 (예: `-> Iterator[Transaction]`, `-> int \| None`) |
| JSONL 선택 이유 / 10만 건 / import 깨진 행 (항목 4) | 이 문서 6장 + `scripts/make_big_data.py` 실측 |

추가 장치:
- 코드에 `# [요구 4.6]`처럼 **미션 요구사항 번호**를 주석으로 표시한다.
- 파일 맨 위에 **"하는 일 / 안 하는 일"**을 적어 책임 경계를 글로 보여준다.
- 이름은 미션 예시를 그대로 쓴다: `Transaction`, `TransactionRepository`, `CategoryStore`, `BudgetStore`, `BudgetService`.

## 3. 폴더 구조와 계층

```
B2-1/
├── budget_app/
│   ├── __main__.py    실행 입구 (python -m budget_app)
│   ├── cli.py         ① CLI: 명령어 해석 → 입력 검사 → 서비스 호출 → 출력
│   ├── prompts.py        대화형 입력 (틀리면 다시 묻기)
│   ├── formatter.py      출력 모양 (표 정렬)
│   ├── services.py    ② 서비스: 기능 규칙
│   ├── storage.py     ③ 저장소: 파일 읽기/쓰기 (JSONL, CSV)
│   ├── models.py      ④ 모델: 데이터 모양 (dataclass)
│   ├── validators.py     입력 검증
│   ├── decorators.py     공통 기능 (오류 처리, 실행 로그·시간)
│   └── errors.py         "원인 + 힌트" 오류 클래스
├── tests/             자동 테스트 (unittest)
├── samples/           import 연습용 CSV
├── scripts/           10만 건 실측 스크립트
├── docs/              설계 문서
├── data/              실행하면 자동 생성
└── README.md
```

**호출 방향은 위 → 아래 한 방향**입니다. (cli → services → storage, 모두 models 사용)

| 계층 | 하는 일 | 안 하는 일 |
| --- | --- | --- |
| ① CLI | 사람과 대화: 명령 해석, 입력, 출력 | 계산, 파일 접근 |
| ② 서비스 | 규칙: 카테고리 확인, id 발급, 검색·요약, 삭제 막기 | 입력 받기, 파일 형식 다루기 |
| ③ 저장소 | 파일 읽기/쓰기 | 규칙 판단 (금액이 맞는지 등) |
| ④ 모델 | 데이터 모양 정의 | 저장, 계산, 출력 |

**"add 명령 하나가 지나가는 길"**
`__main__` → `cli`(명령 해석) → `prompts`(질문) → `validators`(검사) → `services`(카테고리 확인, id 발급) → `storage`(파일 끝에 한 줄 추가) → `cli`(id 출력)

## 4. 데이터 저장 (JSONL, 기본 폴더 `./data`, `--data-dir`로 변경)

| 파일 | 내용 | 한 줄 예시 |
| --- | --- | --- |
| `transactions.jsonl` | 거래 | `{"id": "TX-000001", "type": "expense", "date": "2024-01-15", "amount": 15000, "category": "food", "memo": "점심", "tags": ["meal"]}` |
| `categories.jsonl` | 카테고리 | `{"name": "food"}` |
| `budgets.jsonl` | 월 예산 | `{"month": "2024-01", "amount": 500000}` |
| `recurring.jsonl` | 반복 규칙 (보너스) | `{"id": "RC-001", "type": "income", "day": 25, ...}` |
| `app.log` | 실행 로그 (데코레이터) | `2024-01-15 12:00:00 command=cmd_add exit_code=0 elapsed=0.003s` |
| `backups/<날짜-시간>/` | 백업 (보너스) | 위 4개 파일의 복사본 |

- **초기 실행**: 폴더와 파일이 없으면 자동 생성. 카테고리가 비어 있으면 **(안 A) 기본 카테고리 자동 생성** (food, transport, rent, salary, etc) + 안내 메시지 출력.

## 5. 기능별 결정

| 기능 | 결정 |
| --- | --- |
| add | 대화형. 틀리면 `[오류]`/`[힌트]` 후 그 항목만 다시 질문. 카테고리는 등록된 것만 |
| list / search | 제너레이터로 한 줄씩 → 조건 필터 → `heapq.nlargest`로 최신 N건만 기억. `--limit` 기본 10. 더 있으면 안내 |
| 최신순 기준 | 날짜가 늦은 순, 같은 날이면 나중에 추가한(id 번호가 큰) 것 먼저 |
| summary | 한 줄씩 읽으며 합계만 누적. TOP N은 `Counter.most_common()`. 데이터 없으면 "데이터 없음" |
| budget | `budget set`(설정, 덮어쓰기) + `budget list`(조회). summary에 사용률·초과 경고 |
| category | add / list / remove. **사용 중이면 삭제 막기** (거래 + 반복 규칙 모두 확인) |
| update | **옵션 방식으로 고정**: `update --id <id> [--date] [--type] [--category] [--amount] [--memo] [--tags]` |
| update / delete 저장 | 임시 파일에 쓰고 `os.replace`로 한 번에 교체 (원자적 저장) |
| 없는 id | `[오류] 없는 데이터입니다` + 힌트, 종료 코드 1 |
| import | 행마다 검사 → 깨진 행은 "N번째 줄: 이유" 리포트 후 건너뜀(부분 성공). `--strict`면 하나라도 깨지면 전체 취소. 저장은 마지막에 원자적으로 한 번 |
| export | `--month` 또는 `--from`/`--to` 필수. UTF-8, 헤더 포함, 6컬럼(다시 import 가능) |
| 오류 | 모든 오류는 `BudgetAppError(원인, 힌트)`로 통일. 스택트레이스 없음 |
| 종료 코드 | 0 = 성공, 1 = 실행 중 오류, 2 = 명령 형식 오류 |
| `--help` | 모든 명령·하위 명령에 제공. `-h`는 끄고 `--help`만 (옵션 `--` 통일) |
| 데코레이터 | `@handle_errors`(오류 → 메시지 + 종료 코드 1), `@log_execution`(명령·종료 코드·시간 → `app.log`) |
| 보너스 | backup, recurring(add/list/remove/apply, 중복 방지·말일 보정), 표 정렬(한글 2칸 계산), 원자적 저장 |

## 6. 평가 항목 4 대비 결정 근거

**JSONL을 고른 이유**
- 한 줄 = 거래 1건 → 한 줄씩 읽는 제너레이터와 딱 맞는다.
- 추가는 파일 끝에 한 줄 붙이기만 하면 된다.
- 태그 같은 목록, 쉼표가 들어간 메모도 그대로 저장된다. (CSV는 따옴표 규칙이 필요)
- 단점: 엑셀로 바로 열기 어렵다 → 그래서 export는 CSV로 제공한다.

**10만 건이 되면** (`scripts/make_big_data.py`로 실측)
- 메모리: 스트리밍이라 거의 늘지 않는다.
- 병목: 명령마다 파일 전체를 처음부터 훑는다. (id 발급, 검색, 요약, update/delete의 전체 다시 쓰기)
- 개선 방향: 마지막 id를 별도 파일에 저장, 월별로 파일 분리, 또는 표준 라이브러리 `sqlite3`로 바꾸고 인덱스 사용.

**import에 깨진 행이 섞이면**
- 기본: 정상 행만 등록 + 깨진 행은 줄 번호와 이유를 리포트 (부분 성공).
- `--strict`: 하나라도 깨지면 아무것도 등록하지 않음 (롤백).
- 어느 쪽이든 저장은 마지막에 원자적으로 한 번 → 중간에 실패해도 기존 데이터는 그대로.

## 7. 일부러 단순하게 남긴 것

- 금액은 숫자만 받는다 (`15,000`처럼 쉼표 포함 X).
- delete 확인 질문 없음 (옵션 방식 권장 + backup 제공).
- 외부 라이브러리, 데이터베이스 사용 안 함.
